BASCAL

A structured compiler for classic 1980s Microsoft BASIC. Write .bcl source with real control flow, functions, arrays, and a typed record/file DSL — bcc lowers it straight to plain line-numbered BASIC you can still hand-read and compile with period-accurate tooling like FreeBASIC.

Why BASCAL exists

BASCAL keeps BASIC's global symbol model — variables and functions are still global, still lowered to GOTO/GOSUB — while adding enough structure that larger programs stay maintainable.

Make BASIC more pleasant to write, without pretending it is a different runtime.

It traces back to a preprocessor written for a real BASIC shop in 1985, built to stop copying a shared routine library by hand into every program and to stop remembering which line number a subroutine lived at. BASCAL is a modern reconstruction of that idea in Rust: a real compiler, not a text preprocessor, that still respects the classic BASIC it targets.

What BASCAL adds over raw BASIC

  • Multiline if/else if/else/end if, for/next, while/wend, do/loop
  • function/procedure declarations with explicit return, lowered to global vars + GOSUB
  • Path-style require/import dependencies (dots become directories)
  • select case with ranges and is comparisons
  • program ... suite ... with COMMON-block coordination across chained programs
  • A typed record/file DSL for random-access file I/O — see below
  • Generated .bas output stays hand-readable, with source comments preserved

Record files: hand-written vs the record/file DSL

BASCAL already supported classic random-access file I/O (OPEN ... FOR RANDOM, FIELD, GET/PUT, LSET, MKx/CVx) — writing it by hand is exactly the kind of repetitive, error-prone bookkeeping a compiler should do instead. Every pane on the right below is generated by the pane on the left; the DSL doesn't change what runs, only how much of it you have to type and keep in sync yourself. Full source: tutorial/15_random_and_record_files.bcl.

1. Declare the record shape and open the file

The DSL sums the field widths for you and generates the matching FIELD binding — get one field's width wrong by hand and every record after it reads/writes off by that many bytes.

Hand-written 
const rec_len%  = 30   ' 2+20+8, by hand
const db_file$  = "students.dat"

open db_file$ for random as #1 len = rec_len%
field #1, 2 as idBuf$, 20 as nameBuf$, 8 as scoreBuf$
BASCAL DSL 
record Student
    id:    int16
    name:  string(20)
    score: float64
end record

file db as Student = open("students.dat")

2. Write a whole record

Every declared field is required in the DSL literal — a field forgotten by hand ships silently; a field forgotten in { ... } is a compile error.

Hand-written 
lset idBuf$    = mki%(1)
lset nameBuf$  = "Alice"
lset scoreBuf$ = mkd#(95.0)
put #1, 1
BASCAL DSL 
db[1] = { id: 1, name: "Alice", score: 95.0 }

3. Read records back in reverse order

downto is sugar for step -1; s.id/s.name/s.score resolve straight to the unpacked scalars — no cvi%/cvd#/rtrim$ to remember or mismatch.

Hand-written 
for i% = num_recs% to 1 step -1
    get #1, i%
    id%    = cvi%(idBuf$)
    score# = cvd#(scoreBuf$)
    print "[" + str$(id%) + "] " _
        + rtrim$(nameBuf$) + " -- " + str$(score#)
end for
BASCAL DSL 
for i = 3 downto 1
    let s = db[i]
    print "[" + s.id + "] " + s.name + " -- " + s.score
end for

4. Update a single field

Bob just scraped a pass on re-mark — only the score changes, but PUT always writes the whole buffer, so a GET has to come first either way.

Hand-written 
get #1, 2
lset scoreBuf$ = mkd#(61.5)
put #1, 2
BASCAL DSL 
db[2].score = 61.5

5. Update two fields in one shot

Alice got married and re-sat the exam. Whether the fields you didn't list need a GET first is decided at compile time — the compiler compares the field names you gave against the record's declared fields. Give it every field and the GET disappears entirely, same as a plain { ... }. Misspell a field name and it's still a compile error, not silent data loss.

Hand-written 
get #1, 1
lset nameBuf$  = "Alice Smith"
lset scoreBuf$ = mkd#(91.0)
put #1, 1
BASCAL DSL 
db[1] = ?{ name: "Alice Smith", score: 91.0 }
Hand-written: 4 lines, 3 buffer names, 1 pack call, repeated per edit DSL: 1 line, still exactly one GET + one PUT generated

6. Batched update via read → mutate → write back

Same one-GET-one-PUT shape as ?{ ... } above, spelled as read/mutate/write-back instead — useful when the new values aren't just one-line literals. s.field = value alone is pure in-memory assignment; nothing touches disk until the final write-back.

Hand-written 
get #1, 3
lset nameBuf$  = "Carol Jones"
lset scoreBuf$ = mkd#(88.0)
put #1, 3
BASCAL DSL 
let carol = db[3]
carol.name  = "Carol Jones"
carol.score = 88.0
db[3] = carol

7. Close

Hand-written 
close #1
BASCAL DSL 
db.close()

Nothing above runs slower — every DSL line transpiles to exactly the same OPEN/FIELD/LSET/PUT/GET/MKx/CVx calls shown on the left, generated for you instead of typed and kept in sync by hand. See the Record Files section of the manual for the full semantics, including the exact static rule for when a partial write needs a GET.

Control flow: structured vs hand-rolled GOTO

The record/file DSL is the newest addition, but the same trade lives throughout BASCAL: the line-numbered dialects bcc targets have no SELECT CASE, no DO/LOOP, and no multiline IF — every branch and loop is really just IF ... THEN GOTO threaded by hand. The panes on the left below are what that threading looks like written directly; the panes on the right are what bcc lets you write instead. bcc still generates the GOTO chain — it just generates it correctly, every time, so you never have to count line numbers or trace jumps yourself. Full sources: tutorial/06_select_case.bcl and tutorial/05_loops.bcl.

1. SELECT CASE

Six clauses means six branch targets and a fall-through target to keep numbered and pointed at the right place by hand — miswire one GOTO and a case silently falls into the wrong branch.

Hand-written GOTO 
score% = 85
IF score% = 100 THEN GOTO 250
IF score% >= 90 AND score% <= 99 THEN GOTO 270
IF score% >= 80 AND score% <= 89 THEN GOTO 290
IF score% >= 70 AND score% <= 79 THEN GOTO 310
IF score% >= 60 AND score% <= 69 THEN GOTO 330
IF score% >= 0 THEN GOTO 350
GOTO 370
250 PRINT "Perfect!" : GOTO 380
270 PRINT "A -- Excellent" : GOTO 380
290 PRINT "B -- Good" : GOTO 380
310 PRINT "C -- Satisfactory" : GOTO 380
330 PRINT "D -- Passing" : GOTO 380
350 PRINT "F -- Fail" : GOTO 380
370 PRINT "Invalid score"
380 REM ...
BASCAL 
select case score%
case 100
    print "Perfect!"
case 90 to 99
    print "A -- Excellent"
case 80 to 89
    print "B -- Good"
case 70 to 79
    print "C -- Satisfactory"
case 60 to 69
    print "D -- Passing"
case is >= 0
    print "F -- Fail"
case else
    print "Invalid score"
end select

This is genuinely what bcc emits for the pane on the right — see the generated IF (BCC_T2% = 100) <> 0 THEN GOTO 250 dispatch chain in tutorial/06_select_case.bas. The only difference is a compiler numbered and wired every jump, instead of you.

2. WHILE / WEND

A pre-check loop is one IF ... THEN GOTO guarding the top and one GOTO looping back at the bottom — both have to name the same line number.

Hand-written GOTO 
p% = 1
400 IF p% >= 100 THEN GOTO 440
    PRINT "  "; p%
    p% = p% * 2
    GOTO 400
440 REM ...
BASCAL 
p% = 1
while p% < 100
    print "  "; p%
    p% = p% * 2
end while

3. DO WHILE / DO UNTIL

Same pre-check shape as WHILE, spelled two ways depending on whether the loop-continues condition reads more naturally as a "while" or an "until".

Hand-written GOTO 
k% = 1
670 IF k% > 3 THEN GOTO 700
    PRINT "  "; k%
    k% = k% + 1
    GOTO 670
700 REM ...

k% = 1
740 IF k% <= 3 THEN GOTO 770
    PRINT "  "; k%
    k% = k% + 1
    GOTO 740
770 REM ...
BASCAL 
k% = 1
do while k% <= 3
    print "  "; k%
    k% = k% + 1
end do

k% = 1
do until k% > 3
    print "  "; k%
    k% = k% + 1
end do

4. Post-check loop ("repeat until") and a mid-loop exit

Classic BASIC has no REPEAT/UNTIL either — a loop that must run its body at least once, or that needs to break out from the middle rather than the top, means the continuation test and the jump can't share one tidy spot the way WHILE can. BASCAL's bare do ... end do plus exit do covers both without the loop's exit condition having to live at a fixed position.

Hand-written GOTO 
' body always runs at least once
k% = 99
810 PRINT "  "; k%
    k% = k% + 1
    IF k% <= 3 THEN GOTO 810

' exit from the middle, at k% = 3
k% = 1
910 IF k% = 3 THEN GOTO 970
    PRINT "  "; k%
    k% = k% + 1
    GOTO 910
970 REM ...
BASCAL 
' body always runs at least once
k% = 99
do
    print "  "; k%
    k% = k% + 1
    if k% > 3 then
        exit do
    end if
end do

' exit from the middle, at k% = 3
k% = 1
do
    if k% = 3 then
        exit do
    end if
    print "  "; k%
    k% = k% + 1
end do

for/next gets the same treatment (exit for transpiles to the identical guarded-GOTO shape as exit do above), and multiline if/else if/else compiles to the same nested IF (cond) = 0 THEN GOTO ... chain — see the Condition Lowering note in the README for why BASCAL inverts with = 0 instead of BASIC's bitwise NOT.
